## 3. 系统架构

### 3.1 数据流

```
OV5640 (DVP 8bit, RGB565, ~15 fps 实测)
   │  cmos_pclk 域
   ▼
DVP 采集 / 场行计数 ──► RGB565 → Y8  (Y = (77R + 150G + 29B) >> 8)
   │                     └─► 同时保留 R/G/B 8bit，供彩色 2×2 四点均值
   ▼
3×3 窗口（12 个 line_buffer：灰度 3 行 + R/G/B 各 3 行）
   ▼
Sobel |Gx| + |Gy| → 双阈值迟滞 (48/64) → 时域 2bit 计数确认
   │                     │
   │                     └─► 1bit 边缘历史缓存（frame_buffer，供跨帧确认）
   ▼
2×2 降采样（四点均值）→ 320×240
   ▼
写侧打包：px8 = RGB332；edge ? 8'hE0 : px8
   │  cmos_pclk 域，wframe_data_en 每字节一拍
   ▼
ddr_frame_buffer (u_fb_ddr)
   │  内部 axi4_ctrl：4 块 × 4 MB，帧流式，写地址自增（C_ADDR_INC=1024）
   ▼
DDR3 (K4B4G1646E, x16)
   │  clk_pixel 域，每显示帧顺序读一遍
   ▼
行缓冲 lbuf（1 块 RAM10）→ 2× 最近邻放大 → 640×480 RGB332
   ▼
TMDS 编码 ×3 → HDMI
```

旁路：同一份显示像素在 `THUMB_RAW` 控制下写入 64×48 的 `ssram`，由 UART 以 115200 回传（约 1.5 fps）。

### 3.2 时钟域

| 时钟 | 频率 | 来源 | 用途 | 约束/备注 |
|---|---|---|---|---|
| `clk_sys` | 96 MHz | `hdmi_pll` = **PLL_TL0** | 心跳、LED、UART、AXI 主控、看门狗 | — |
| `clk_pixel` | 25.2 MHz | 同上 | 640×480@60 显示时序 | 25.2 M / (800×525) = 60.0 Hz |
| `clk_pixel_10x` | 126 MHz | 同上 | TMDS 串行 | **硬约束 ⇒ 分辨率只能 640×480@60** |
| `cmos_pclk` | ~28 MHz | `GPIOT_P_07` 输入 | DVP 采集、Sobel、写 DDR | 与 `clk_sys` 同数量级但**异步** |
| `tdqss_clk` | 384 MHz | `ddr_pll` = **PLL_BR0** | DDR3 DQS 采样 | 最紧域，2.604 ns |
| `core_clk` | 192 MHz | 同上 | DDR 控制器核心 | — |
| `tac_clk` | 384 MHz | 同上 | DDR 读捕获 | **不要把逻辑插进这个域** |
| `twd_clk` | 384 MHz | 同上 | DDR 写 | — |

`ddr_pll` 参考 `clk_sys` 96 MHz，M/N/O = 2/1/1。

### 3.4 DDR3 通路关键事实（血泪总结）

1. **`axi4_ctrl` 是帧流式的，不能随机寻址**：没有写地址输入，写地址 = 断言 `data_en` 的顺序；`rc_w_ptr += C_ADDR_INC`（64×16=1024）。
2. **4 块 × 4 MB buffer，读跟写**：读指针只走到刚写满的那块；读写撞块在机制上被挡住。
3. **`wframe_data_en` = 每字节一拍**；`rframe_data_en` = **提前 1 拍**取数请求；`*_vsync` = **下降沿 flush**。
4. **EOF 时 FIFO 未满会先补满 1024 B 再归零**：75,922 不整除 1024 只浪费带宽，不污染下一帧。
5. **52 根 DDR 引脚**：`addr[15:0]` + `ba[2:0]` + `dq[15:0]` + `dqs[1:0]` + `dqs_n[1:0]` + `dm[1:0]` + 命令 7 + `clk_p/n` + **`verf0` / `vref1`（官方就拼成 `verf0`）**。全部 1.5 V SSTL + register。
6. 引脚定义**两份必须同步改**：`camera_hdmi.peri.xml`（build 的 `--peri_file` 消费它）+ `camera_hdmi.isf`（权威定义）。
7. **不要导入官方 `pinout.csv`** —— 缺 `register_option` / `clock_name` / 动态延迟。
8. DDR 时序最紧的是 `tac_clk`（2.604 ns）。**不要往 DDR 时钟域插逻辑**。

**带宽账本（不是瓶颈）**

| 方向 | 速率 | 占用 |
|---|---|---|
| 写 | 15 fps × 75,922 B ≈ **1.14 MB/s** | 可忽略 |
| 读 | 60 fps × 75,922 B ≈ **4.56 MB/s** | 可忽略 |
| DDR3 理论 | ~1.6 GB/s | 余量 300× |

⇒ 抽动**不是带宽问题**，不要往这个方向查。

### 3.5 像素账本（对不上就会错行）

```
写：srow = row_d1>>1      (2..476 偶)  → 0..238
    scol = (pcol-2)>>1    (pcol=2..638 偶) → 0..318
    地址 = srow*320 + scol
    ⇒ 319 列 × 238 行 = 75,922 B/帧

读：drow_raw = dy_d[8:1] (0..239)，0→1、239→238
    dcol = dx[9:1] (0..319)，319 镜像到 318
    ⇒ 序列必须单调不减（318 的镜像不能删！）
```

### 5.4 帧格式与状态字

```
帧头：'@' + 帧号(2 hex) + 状态字(2 hex) + CR LF
帧体：48 行 × (64 字节 → 128 hex + CRLF)
```

状态字 8 位：

| bit | 含义 |
|---|---|
| 0 | `hdmi_pll` 锁定 |
| 1 | `ddr_pll` 锁定 |
| 2 | `cal_done` |
| 3 | `cal_pass` |
| 4 | `cfg_done`（SCCB 配置完成） |
| 5 | DVP 有像素 |
| 6 | 有任何 SCCB ACK |
| 7 | 恒 1（版本指纹 ver2） |

**全健康 = `FF`**。`F7` = `cal_pass` 瞬时为 0，通常下一帧恢复。

### 5.5 LED 判读

6 颗，**从板右侧起依次 `led[0]…led[5]`，低电平点亮，亮 ⇔ 位=1**。

| 灯 | 含义 |
|---|---|
| `led[0]` | `hdmi_pll` 锁定 |
| `led[1]` | `ddr_pll` 锁定 |
| `led[2]` | SCCB ACK（⚠️ **粘性 0，灭是误报，不要当判据**） |
| `led[3]` | DVP 有像素（**以它为准**） |
| `led[4]` | `cal_done` |
| `led[5]` | `cal_pass`：常亮=过；快闪 5.7 Hz=跑了没过；慢闪 1.4 Hz=没跑完；**永不常灭** |

上电有 0.5 s 全灭 + 每 0.5 s 多亮一颗的扫灯自检，**判读前等 ≥5 s**。
`SELFTEST=1` 时 `led[2..4]` 报首错桶号、`led[5]` 报"零错/有错"。

**⚠️ 核心板 8 颗灯里只有 6 颗是我们的**：`LED6`=R3、`LED7`=R4 与 `cmos_d[0]/d[1]` 同球，会跟着像素乱闪，不是判据。

## 7. 已知问题

### 7.1 【P0 · 待解决】画面抽动（judder）

> **这一节是本次交接的核心待办。请优先定位并修复。**

#### 7.1.1 现象

- HDMI 上画面整体**一顿一顿**地更新，像"每秒只有十几帧"；转动镜头或移动物体时最明显。
- **不是**撕裂（没有上下半屏来自不同帧的错位线）。
- **不是**错行/错列（静态画面结构完整）。
- **不是**几何抖动（实测帧间位移 **0.00 px**）。
- 伴随轻微**亮度闪**：画面中段均值在 121.x ↔ 124.x 两档之间跳（≈1 个 3-bit LSB），频率约 3 Hz。

#### 7.1.2 量化证据（已做）

对用户提供的 2.62 s / **157 帧 @60.02 fps** 手机录屏（720×1280 竖屏拍显示器）分析：

| 指标 | 结果 | 含义 |
|---|---|---|
| 相邻帧"全幅平均绝对差"序列 | 呈 `6.6 → 4.4 → 2.7 → 0.5 → 0.4` 的**周期性衰减脉冲** | 新帧到达后要 3 帧才稳定 |
| 刷新事件中位间隔 | **4.0 个视频帧 ⇒ 15.0 Hz** | 每帧在屏上停约 4 个显示帧 |
| 刷新事件数 | 157 帧内 **39–40 次** | 与 15 Hz 一致 |
| 低通 k=8 后 | 4 次事件，中位 1.40 Hz | 缓慢变化（AEC） |
| 低通 k=16 后 | 8 次事件，3.16 Hz | 亮度阶梯 |
| 最大变化帧的亚像素位移 | **+0.00 px** | 排除画面整体抖动/滚动 |
| 频谱峰 | 10.63 Hz | 手机拍屏幕的摩尔纹拍频，**不是**刷新率 |

**结论（数据层面）**：内容刷新约 **12–15 Hz**，而显示器是 **60 Hz** ⇒ 每个采集帧被重复显示 4–5 次，运动必然是阶梯状 ⇒ 这就是"抽动"的直接来源。

#### 7.1.3 影响范围

| 维度 | 是否受影响 |
|---|---|
| 单帧画面正确性（颜色、边缘位置、分辨率） | ❌ 不受影响 |
| DDR3 读写正确性 | ❌ 不受影响（已用 1:1 窗口验证） |
| 640×480 输出时序 | ❌ 不受影响（60 Hz 稳定、无位移） |
| 实时观感 / 演示视频 | ✅ **明显受影响** |
| 快速运动场景的可用性 | ✅ 受影响（会出现"跳格"） |

⇒ 不影响功能验收，但**影响演示效果与"实时性"这一评分点**，必须解决。

#### 7.1.4 已排除的方向（不要再查）

1. **DDR3 带宽**：读 4.56 MB/s + 写 1.14 MB/s，余量 300×。
2. **DDR3 误码**：1:1 窗口帧间 72% 逐位相同、灰度只落在 RGB332 网格、无 64/128/1024 周期。
3. **TMDS / 显示时序**：60 Hz 稳定；最大变化帧亚像素位移 0.00 px。
4. **帧缓存撕裂**：读侧只在显示帧起始切 bank，整帧来自同一块。
5. **PLL 失锁 / 校准**：状态字长期 `FF`，六灯全亮。
6. **`axi4_ctrl` 的 FIFO 参数**：与官方逐字节一致，不是我们改坏的。

#### 7.1.5 候选根因（按可能性排序，**尚未定论**）

**R1（最可能）：传感器实际只有 ~15 fps，60 Hz 显示 ⇒ 4:1 保持**

`ov5640_cfg_rom.v` 当前配置：

| 寄存器 | 值 | 含义 |
|---|---|---|
| `0x380C/0x380D` | `0x07/0x68` | HTS = **1896** 像素/行 |
| `0x380E/0x380F` | `0x03/0xD8` | VTS = **984** 行/帧 |
| `0x3808..0x380B` | 640 × 480 | 有效分辨率 |
| `0x3035` | `0x21` | 系统时钟分频 2 |
| `0x3036` | `0xA0` | PLL 倍频 160 |
| `0x3037` | `0x12` | 预分频 2 + 根分频 2 |

自洽性检查：1896 × 984 = 1,865,664 像素/帧；若 PCLK ≈ 28 MHz，则帧率 = 28e6 / 1,865,664 ≈ **15.0 fps** —— 与实测 15 Hz 完全吻合。
**15 fps 在 60 Hz 屏上只能每帧重复 4 次，物理上不可能平滑。**

**R2：帧率不是整数比 + AEC 动态改 VTS**

即使传感器是 30 fps，若实际为 29.x fps，或 AEC 在暗光下把 VTS 拉长（帧率在 30/15 之间切换），就会出现"2 帧/3 帧保持"交替的 3:2 pulldown 式抖动。实测刷新间隔出现 2/3/5/7 帧的离散分布，符合这一类特征。

**R3：写完成 → 读切换的相位差**

`axi4_ctrl` 的读指针在 `rframe_vsync` 下降沿才切到"最新写满的块"；而 `rd_frame = disp_frame_start` 只在显示帧起始生效。若某帧写完的时刻刚好落在显示帧起始之后，就要**多等一整帧**才被显示 ⇒ 偶发多停 1 帧。`done_toggle`/`pending` 链路本身有 2 级同步延迟。

#### 7.1.6 定位步骤（建议按顺序做，1 与 2 可并行）

**Step 1（不改 RTL，最快）：用 240 fps 慢动作复测**

用手机慢动作（240 fps）拍屏幕 3 s，直接数"同一画面停留多少个 240 fps 帧"：

- 16 帧 ≈ 15 fps 源
- 8 帧 ≈ 30 fps 源
- 4 帧 ≈ 60 fps 源

这一步能在 5 分钟内把 R1 与其他假设分开。

**Step 2（改 RTL，最确定）：加帧周期遥测**

在 `ddr_frame_buffer.v` 里用 `cmos_pclk` 或 `clk_sys` 统计相邻 `wframe_vsync` 下降沿的周期，做 1024 分频后接到 `tp_o[31:0]`，用 Efinity Debugger 的 **Logic Analyzer / VIO** 抓 1 s：

```verilog
// 建议接线（示意）
// tp_o[31:16] = 写帧周期（分频后）
// tp_o[15:8]  = 每秒 EOF 数
// tp_o[7:0]   = 每秒 rd_bank 切换数
```

判据：

| 观测 | 结论 |
|---|---|
| 写帧周期 ≈ 66.7 ms（≈15 fps） | R1 成立 |
| 写帧周期 ≈ 33.3 ms，但 `rd_bank` 每 4 个显示帧才变一次 | R3 成立 |
| 写帧周期在 33/66 ms 之间跳 | R2 成立 |

**Step 3：读代码确认切换时机**

重点看三处：

- `camera_hdmi.v` 第 9a 节：`done_event` / `pending` / `rd_bank`（`(hcnt==0 && vcnt==0)` 才切）；
- `camera_hdmi.v` 8b 节：`rd_frame(disp_frame_start)`；
- `ddr_frame_buffer.v` 的 `rframe_vsync_r` 生成。

确认"一帧写完后，最早能在第几个显示帧起始被读到"。

#### 7.1.7 修复方案（按根因选择）

**若 R1 成立（15 fps 源）**

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| **A（推荐）提高到 30 fps** | 把 `0x380E/0x380F` 从 `0x03D8`(984) 改为 `0x01EC`(492) | 最大曝光行数减半 ⇒ 暗光下更暗/增益更高；需重验 `cal_pass` 与画面亮度 |

- 必要时把 `0x3035` 的 PLL 分频改成整数倍关系。

**若 R3 成立（相位差）**

- 缓冲深度 4 块足够，不需要加深。

1. 240 fps 慢动作：同一画面停留帧数稳定（30 fps 源 = 8 帧），**不出现 8/12 交替**；

3. 肉眼：缓慢平移镜头，画面连续、无"跳格"；

5. 时序：四步 `exit=0`、违例 0、RAM10 ≤ 160；
6. 单帧正确性不回退（红边闭合、颜色正常）。

### 7.2 【P1】AEC 亮度回摆

- **现象**：帧间均值在 **227.3 ↔ 203.3** 两档之间跳（另一场景是 121/124 微跳）；亮态时约 45% 像素饱和成死白。
- **原因**：ROM 里没有 `0x3503`（手动曝光），OV5640 自动曝光在追光。
- **影响**：演示视频里亮度闪；也会放大 7.1 的"抽动感"。
- **修法**：ROM 增加 `0x3503=0x03`（关 AEC/AGC）+ 固定增益 `0x350A/0x350B`；建议与 7.1 一起做。
- **注意**：固定曝光后暗场景会偏暗，需要在目标演示环境下标定一组值。

### 7.3 【P2】RGB332 棋盘 / 色带

- 全屏 2 像素棋盘格，幅度 = 1 个 3-bit LSB；`(r+c)` 偶格均值 150.7、奇格 170.8。
- 原因：RGB332 的 R/G 两个 3-bit 通道量化不同步 + `CDITH=1` 的 4×4 Bayer。
- 影响：暗部观感有细纹；**不是 DDR 错误**（真错会是 64/1024 周期或整行错位）。
- 可选：`CDITH=0` 看是否更干净（会出色带）；或改 RGB565 存储（需要 2 字节/像素，DDR 容量完全够，但要改读写位宽与行缓冲）。

### 7.4 【P2】`rframe_data_en` 提前 1 拍 off-by-one

- 读侧每行第 1 个字节可能取到上一行末尾，**只影响最左 1 列**，肉眼不可见。
- 修法：把 `rdata <= rd_fetch ? rframe_data : lbuf[rd_col]` 的取数条件与 `rd_col` 对齐；改完必须重跑 `_raw11.py` 确认相关不降。

### 7.5 【P3】`led[2]` 语义错误

- `ack_ok` 在 `i2c_ov5640.v` L202 是**粘性 0**，所以 `led[2]` 灭是误报。
- 判据一律用 `led[3]`（DVP 有像素）与状态字 bit5/bit6。

### 7.6 【P3】`MEDIAN` 参数只声明无实现

- 中值滤波没有实际逻辑；不要以为置 1 就生效。若要覆盖"中值滤波"这一项，需要真正实现 3×3 中值（资源足够，RAM10 只用了 148/256）。

## 9. 红线（违反会直接坏板/坏工程）

1. **不要升级 IP**。所有 IP 保持 `2022.2.322`；Efinity 提示升级一律点 No。2022.2 → 2026.1 的 baseline 已通过，升级会破坏它。
2. **不要改 `W0_FIFO_8` / `R0_FIFO_8` 参数**（`PROG_EMPTY_ASSERT=127`、`ASYM_WIDTH_RATIO=8`），与官方逐字节一致。
3. **不要往 `tac_clk`（2.604 ns）域插逻辑**。
4. **不要改 `ddr_frame_buffer.v` 的 `if (we) waddr_d <= waddr;`**，也不要改 `camera_hdmi.v` 的 `if (fb_we_r2) tb_addr_d <= fb_addr_r2;`。
5. **不要删读侧 `dcol` 的 318 镜像**（会让行缓冲整体错位一格）。
6. **SDC 必须是 171 行版**：`efx_pnr --sdc_file` 只加载指定文件，9 个时钟（含 `clk_pixel_10x {0.496 4.465}`、`twd_clk {0.651 1.953}` 相位）必须自己 create；`clk_sys↔clk_pixel` 必须显式 `set_false_path`（**不能用 `set_clock_groups`**，会误断 `clk_pixel↔clk_pixel_10x`）。
7. **不要改 52 根 DDR 引脚定义**；`peri.xml` 与 `.isf` 两份必须同步。
8. **不要导入官方 `pinout.csv`**。
9. **烧完不要按 K3**；`K1`=CDONE、`K2`=CSI/CSO、`K3`=CRESET_N，全是配置开关。
10. **不要硬编码 COM 口**；每次先枚举 `USB-SERIAL CH340`。
11. **串口 0 字节 ⇒ 先怀疑 SRAM 配置丢了**，重烧 `.bit`，不要先怀疑接线。
12. **产出物里不要写"板子哪天能用/不能用"**（项目约定：板卡交换很容易）。

## 10. 附录

### A. 串口协议

```
波特率 115200, 8-N-1
帧头  ：'@' (0x40) + 帧号 2 hex + 状态字 2 hex + 0x0D 0x0A
帧体  ：48 行，每行 64 字节 → 128 个 hex 字符 + 0x0D 0x0A
节流  ：每帧约 0.54 s 发完 ⇒ 约 1.5 fps
```

### B. DDR 像素账本

```
写：319 列 × 238 行 = 75,922 B/帧
读：dcol 0..318（319 镜像到 318），drow 0..239（0→1、239→238）
C_RD_END_ADDR = 76800（留余量）
C_ADDR_INC    = 64 × 16 = 1024
4 块 × 4 MB buffer，读跟写
```

### C. 第 42 轮根因复盘（最重要的历史教训）

**现象**：DDR 回读画面帧间只有 4 种、其中 3 种是均匀随机噪声，均值在 166/198.9/75.7/204 循环。

**根因**：

```verilog
wire [8:0] scol = (pcol - 10'd2) >> 1;   // pcol 在行消隐被清 0 ⇒ (0-2)>>1 = 511
wire [16:0] fb_addr_c = srow*320 + scol;
```

地址序列变成 `320r+318 → 320r+511 → 320(r+1)+0`，下一行首地址更小；而 `waddr_d <= waddr` **每拍都更新**（含消隐），于是 `w_addr_wrap = we && (waddr < waddr_d)` **每行都成立** ⇒ 每帧误发 238 次 EOF ⇒ `rc_w_ptr` 每行归零、不换块 ⇒ 整帧只写进前 ~1 KB，其余读的是 DDR 上电随机值。

**修复**：`waddr_d` 只在 `we` 时更新（两处）。修复后帧间稳定、真实场景可辨。

**教训**：**"每拍更新"的比较基线在有空闲拍（消隐）的流式接口里是错的**。任何 `x < x_d` 的回绕判据，都要确认 `x_d` 只在有效拍更新。

### D. LED 位置与判据

| 物理位置（从板右起） | 信号 | 正常 |
|---|---|---|
| 第 1 颗 | `led[0]` hdmi_pll | 亮 |
| 第 2 颗 | `led[1]` ddr_pll | 亮 |
| 第 3 颗 | `led[2]` SCCB ACK | 可能灭（误报） |
| 第 4 颗 | `led[3]` DVP 像素 | 亮 |
| 第 5 颗 | `led[4]` cal_done | 亮 |
| 第 6 颗 | `led[5]` cal_pass | 常亮 |

### E. 术语

| 术语 | 含义 |
|---|---|
| EOF | 一帧写完（`wframe_vsync` 下降沿） |
| bank / 块 | DDR 里一块 4 MB 帧缓存，共 4 块 |
| 1:1 窗口 | `THUMB_RAW=1`，中央 64×48 原始字节 |
| 抽动 / judder | 画面按低帧率阶梯更新，非撕裂、非抖动 |
| 拍频 | 5:1 抽点遇到细结构产生的假周期 |

## 11. 交接结论

- **能交付的部分**：DDR3 帧缓存 + 彩色边缘检测的完整链路、可复现的构建与上板流程、完整的串口/LED 诊断体系。
- **不能交付的部分**：流畅的实时观感（7.1）、固定曝光（7.2）、演示视频。
- **接手后的第一件事**：用 240 fps 慢动作确认源帧率，按 7.1.6 判定 R1/R2/R3，再动 RTL。
- **最容易被误导的三个坑**：① 串口缩略图是 5:1 抽点，不能判字节；② `led[2]` 灭是误报；③ Programmer 看不到设备是 USB 驱动绑定问题，不是板子坏了。
